# 配置编辑与更新

从内核 `mihomo-optimized-v1.0.0`、面板 `0.4.0` 起，面板来源和安装目录固定。面板与内核的自动更新都由 mihomo YAML 控制，设置页不提供路径、URL、自动更新开关或间隔输入。自内核 `1.0.4`、面板 `0.4.6` 起，增加统一“检查并更新”按钮，真实执行配置中资源的检查和安装。面板源码仍在 `clash-dashboard` 分支，静态文件在 `clash-dashboard-dist` 分支。

内核 `mihomo-optimized-v1.0.1` 新增启用项目的启动 / 重启时立即异步检查。完整配置与本项目新增 DNS 字段见 [README 配置示例](../README.md#完整配置示例)，旧字段的永久忽略、条件停用与校验拒绝见[迁移表](../README.md#旧配置迁移与停用范围)。

## 编辑当前配置文件

设置页点击“编辑配置”，读取当前内核正在使用的普通 UTF-8 YAML 文件。沿用原有 `external-controller` / `secret` 设置，不新增配置编辑开关。API 沿用控制器原有鉴权：

| 请求 | 含义 |
| --- | --- |
| `GET /configs/file` | 返回 `path`、`content`、`revision`、`max_size`、`writable` |
| `PUT /configs/file` | JSON 提交 `content` 和读取时的 `revision`，保存后返回新的文件及修订标识 |
| `PUT /configs?force=true` | JSON 提交 `{}`，读取当前配置文件，执行完整校验和重载，并更新可热重载的入站监听设置 |

从内核 `mihomo-optimized-v1.0.2` 起，成功读取和保存的响应包含布尔字段 `writable`。这是基于当前进程权限及安全替换条件的预检查：文件必须可写，所在目录需允许创建和替换，且能够保留原属主、组和访问控制。可读取但不满足保存条件时，GET 仍返回内容和 `writable: false`，不会为探测权限修改配置或创建临时文件。

面板 `0.4.4` 收到 `writable: false` 后立即显示只读，支持选择、复制，禁止输入、Tab 缩进、保存与 Ctrl-S / Cmd-S。例如配置由 root 持有而服务以 mihomo 运行，且服务无法保留原文件属主时，应先显示只读。编辑期间权限变化导致 PUT 保存被拒绝（包括失去读取权限），HTTP `403` 返回固定 `code: config_file_read_only`；GET 无权读取时返回 `config_file_access_denied`。保存权限错误会让面板保留草稿并转为只读，与控制器鉴权失败分别提示。修复权限后重新读取会重新检查；旧内核缺少 `writable` 时保留原编辑行为。

权限预检查不能保证后续保存一定成功，实际保存仍重新检查并保留原文件。手机编辑器铺满可用视口并适配安全区域；打开及重新读取从第一行、第一列显示，保存响应不重置光标或滚动位置。

**面板 `0.4.2` 的主按钮为“保存并重新加载”，Ctrl-S / Cmd-S 执行同一操作。** 面板先调用保存接口，收到有效的文件及新修订标识后，再对同一控制器发起完整重载；重载成功后才提示整个操作完成。两阶段期间阻止重复提交，切换控制器后取消旧会话及后续界面回调。

组合操作使用 `force=true`，使 HTTP / SOCKS / mixed 端口、绑定地址及 `allow-lan` 等可热重载设置随文件应用；原有独立“重新加载配置”入口保持原行为。`external-controller`、控制器 `secret` 等启动设置不在热重载范围，修改后仍需重启内核。

保存成功而重载失败时，文件及新的修订标识继续保留，编辑器提示已保存但重载失败或结果无法确认，可以修正内容或重试；重试仍先检查当前文件修订，避免覆盖别人的修改。保存与重载不是同一个原子事务，重载失败不会自动回滚磁盘文件。

从面板 `0.4.7` 起，保存后的重载与独立重载请求都最多等待 30 秒。超时后恢复界面操作，编辑器保留已保存的文件和重载重试入口；网络超时只表示浏览器未确认结果，不能断言内核没有应用配置。重载 PUT 成功后的设置刷新在后台执行，刷新失败或迟迟未返回不会把已完成的重载变成失败，也不会继续锁住操作。

底层保存接口仍只检查单个 YAML 映射及基础字段类型，不调用运行态配置解析或应用，也不下载 providers。单独读取或保存文件不会清 DNS 缓存、重置观测或中断连接；组合按钮随后执行的完整重载沿用内核既有处理。直接修改磁盘文件或只调用 `PUT /configs/file` 后，仍需另外完整重载。

不接受任意文件路径。当前配置超过 4 MiB、使用 AGE 加密、非 UTF-8、文件不是普通文件或路径中包含符号链接时，编辑器显示相应限制。嵌入模式禁用该接口。草稿和修订标识仅保留在页面内存，关闭或切换控制器即释放；服务端响应包含 `Cache-Control: no-store`，错误不回显 YAML 或凭据。

保存请求使用单操作闸门，忙时返回 `503` 而不积压配置缓冲。文件变化后返回 `409`，面板保留草稿；单次写入采用同目录临时文件、同步与替换，并保留原权限和属主。Linux 额外保留 POSIX 访问 ACL，Windows 保留属主、组及 DACL。无法保留这些访问权限时不替换原文件。

文件身份、路径及内容修订在替换前重新检查。编辑器请求之间具有冲突保护；不共享此操作锁的外部程序仍可能在最后检查与文件替换之间写入，不承诺跨进程的文件事务。完整重载与直接修改磁盘文件仍按原有方式使用。

## 统一检查并更新接口

从内核 `mihomo-optimized-v1.0.4`、面板 `0.4.6` 起，设置页的“版本与更新”显示内核、面板版本，规则集和 GeoData 结果，以及从 YAML 读取的自动更新策略。按钮为 **“检查并更新”**：会访问远端并应用实际变化，内核有新版时最后升级并重启。

| 请求 | 行为 |
| --- | --- |
| `POST /upgrade/check` | 空请求体且不带查询参数，启动实际更新任务，返回 `202` 和任务状态；已有统一任务时返回同一任务，不创建并行安装 |
| `GET /upgrade/check` | 读取当前配置元信息及任务结果，返回 `200`；本身不访问更新源、不下载或安装 |

两个方法使用控制器既有鉴权，响应 `Cache-Control: no-store`。路径、来源、通道及强制降级选项均不能由这个请求传入。面板打开时只发 `GET`，用户主动点击才发 `POST`；浏览器不直接请求 GitHub，也不会向发布源转发控制器密钥。旧核心没有此接口时明确提示升级，不回退到浏览器下载或逐个安装接口。

面板每次点击会同时附带 `Idempotency-Key`（随机的 32 位小写十六进制请求标识）和 `X-Mihomo-Instance-ID`（最近 GET 返回的进程身份）。即使浏览器在尚未收到响应时自行重放空 POST，也使用同一标识。内核保存本进程最近 128 个已接受标识：当前任务的重放返回同一任务，已经被后续任务覆盖的旧标识返回 `409 / request_already_seen`；进程身份已改变则返回 `409 / instance_changed`，不会在刚重启的内核中再次执行。两个头必须成对提供；命令行调用可同时省略，此时只具备运行中任务合并，不具备请求标识去重。

任务响应包括：

- `instance_id`：进程身份，重启后改变；`task_id`：这次接受的更新任务。
- `request_id`：创建该任务的 `Idempotency-Key`；不带标识的调用省略此字段。面板用它确认丢失响应后找回的是本次请求，而不是其他终端刚开始的任务。
- `state`：`idle`、`running`、`completed`、`partial` 或 `restarting`。
- `started_at` / `finished_at`：RFC3339 时间（尚未开始或结束时省略）。
- `items`：每项的 `id`、`kind`、`name`、`status`，可选当前 / 远端版本、只读自动策略及错误原因。`kind` 为 `rule-provider`、`geodata`、`ui`、`kernel`。
- `status`：`pending`、`checking`、`updated`、`up_to_date`、`skipped`、`error` 或 `restarting`。`update_interval` 配合 `interval_unit` 读取：规则集为秒，GeoData / UI / 内核为小时。

### 四类资源的下次自动检查时间

从内核 `1.0.10`、面板 `0.4.8` 起，设置页在自动更新已开启时，分别显示**内核、面板、GeoData、规则订阅**的下次检查时间。GeoData 和规则订阅的折叠标题显示本类最近的一次计划；展开后每个数据库、每条订阅仍显示自己的时间。GeoData 各数据库共用当前 GeoData 计时器，规则订阅则使用各自的实际计时器及失败退避时间。

每个 `items` 元素可包含以下实时调度字段；它们与上一次手动“检查并更新”的执行结果独立，每次 `GET /upgrade/check` 都重新读取当前生效的调度：

| 字段 | 含义 |
| --- | --- |
| `next_check` | 实际计时器的下一次周期检查时间，UTC RFC3339；没有已安排的下一次检查时省略 |
| `next_check_in_ms` | 距上述计时器触发还剩的毫秒数；使用内核单调时钟计算，已到期为 `0`，没有计时器时省略 |
| `auto_update_state` | `scheduled` 已安排、`waiting` 等待自动操作开始、`checking` 自动检查中、`retrying` 已安排失败后的重试、`unscheduled` 策略开启但当前无可执行计划 |

页面使用浏览器的当前时钟，将实际剩余时间转换为当地日期、时间和时区；不使用路由器的时区，也不要求路由器的日历时钟与浏览器一致。显示以本次状态请求发起时为锚点，请求和缓存经过的时间会消耗剩余量，不会把慢响应当作新一轮计时；受往返耗时影响，显示时间可能比实际触发略早，最多约一个请求往返。只有绝对时间字段的旧接口仍按浏览器时区格式化；完全没有调度字段的旧内核显示“尚未提供”，不会按页面打开时间加更新间隔猜测。

启用自动更新时，页面在前台每 30 秒只读刷新调度；手动任务执行中继续使用原有进度轮询。重新切回页面会刷新状态。已到计划时间但尚未收到新状态时，显示等待内核确认，不能据此宣称已执行或更新成功；读取失败时标记状态暂时无法刷新。检查时间仅代表计划检查，发现版本或资源内容变化后才会实际安装。

关闭自动更新后不再显示下次时间。等待启动、正在检查、没有使用的数据库、本地规则和未实际启动的工作器分别按真实状态显示；规则订阅正在请求、尚未安排下一轮计时器时，不虚构完成后的时间。内核、面板和 GeoData 的相同策略重载仍保留原计时器；规则订阅保留原有重载行为。手动更新不重置已有自动计时器，规则订阅的下一次检查也不能简单由“最后更新时间 + 间隔”反推。

一次手动任务不修改 YAML 或定时器；即使某项自动更新关闭，也会主动检查该项。任务按当前已加载配置中的 HTTP rule-providers、实际使用的 GeoData、固定来源面板、固定发行内核依次处理。每项失败独立记录，之后继续检查其余项目；本地 / 内联规则或未使用资源显示跳过，不虚构远端版本。规则集更新引入新的 GeoData 依赖时，同一任务随后也会检查该数据库。

规则集与 GeoData 没有统一发行版本，按内容摘要识别变化；相同内容返回 `up_to_date`，变化内容通过解析或数据库校验后再原子保存、发布规则或切换缓存。面板与内核始终比较版本号，仅严格新版安装；面板受管目录缺失或为空时允许初始安装。当前版本无法可靠比较时返回明确错误，不自动改用摘要覆盖面板或内核。

统一任务在资源处理期间占用内核升级门禁，避免另一个自动内核升级中途重启。已有面板或 GeoData 安装时，在本阶段的超时内等待其结束，再进行本次检查。文件下载使用有界超时，不持有配置重载锁；提交前核对配置快照和取消状态。整体任务上限为 10 分钟，各执行阶段最多 3 分钟，具体下载器还可有更短限制。完整重载会取消旧配置未提交的工作，已经成功生效的其他项目不回滚。

内核成功升级后报告 `restarting`，再沿用已有安装 / 重启事务退出旧进程。重启会中断现有连接、重建纯内存 DNS 状态；各项资源处理结束后才进入此阶段。面板仅在新进程报告的实际版本等于旧任务声明的目标时确认内核升级成功，断线本身不代表成功。请求响应丢失时只用 `GET` 找回任务，不自动重发 `POST`；无法找回任务则显示结果未确认。

从内核 `1.0.6` 起，必须完成透明代理保护及旧后端清理后才报告 `restarting`。如果二进制已经安装、但重启准备失败，分项返回 `status: error`、`error: installed_restart_failed`、`installed_version` 和 `pending_restart: true`；`current_version` 继续表示当前仍在运行的旧版本，任务正常结束为 `partial`。内核日志也记录该区别。面板 `0.4.7` 显示通用失败提示并引导查看日志。安装器保留待重启保护，不会在旧进程中重复覆盖新文件；解决保护错误后可再次发起内核重启。

关闭页面、切页或切换控制器只取消浏览器查询，不取消已接受的内核任务。返回该控制器可以重新读取进度。任务历史只保留内存中的最近一次，内核重启后不保留完整历史。面板更新不会主动刷新页面或丢弃编辑草稿；方便时可刷新使用新静态文件。

独立内核安装正在进行时，新的统一任务返回 `409` / `busy`；尚无已加载配置时返回 `503` / `configuration_unavailable`。分项错误使用固定标识，例如 `busy`、`timeout`、`configuration_changed`、`version_unavailable`、`update_failed`，不向面板回显来源凭据或原始下载 URL。

## GeoData 自动更新调度

GeoData 使用原有顶层 YAML 字段，默认关闭，间隔默认 24 小时：

```yaml
geo-auto-update: true
geo-update-interval: 24
```

从内核 `1.0.5` 起，`geo-update-interval` 接受 `1` 至 `2562047` 的整数小时，拒绝零、负数、小数、字符串和超过计时器范围的值。关闭检查使用 `geo-auto-update: false`。

| 操作 | GeoData 自动调度 |
| --- | --- |
| 进程启动 / 重启或从关闭改为开启 | 等待配置和网络就绪，检查实际使用数据库的更新时间；缺失或过期时立即尝试更新，然后保留周期检查 |
| 完整重载相同开关、间隔 | 保留原计时器；旧配置下载被取消，后续检查使用新配置中的来源与实际依赖 |
| 保持开启，仅修改间隔并完整重载 | 取消旧自动任务，按新间隔重新计时，不追加一次立即下载 |
| 关闭并完整重载 | 取消该类自动任务，停止后续自动检查 |
| 获取文件状态或首次下载失败 | 记录错误，保留后续周期检查，不永久退出调度器 |

启动检查只参考实际使用的数据族；不用的 GeoIP、MMDB、ASN 或 GeoSite 文件不会左右其他数据库的到期判断。数据库内容相同仍不会替换文件，更新提交继续受当前配置事务保护。面板主动“检查并更新”和兼容的手动接口保持原行为，不受自动开关限制。

## 在 YAML 中配置面板和内核自动更新

以下四项与 GEO 自动更新配置一样放在 YAML 顶层，间隔单位为小时：

```yaml
external-ui-auto-update: true
external-ui-update-interval: 24
core-auto-update: true
core-update-interval: 24
```

两组开关均默认 `false`，间隔均默认 `24`。间隔接受 `1` 至 `2562047` 的整数小时；零、负数、非整数、带单位的 `24h`、字符串 `"24"` 或超过计时器范围都会导致配置校验失败。`6` 表示每 6 小时检查，`168` 表示每 7 天检查。可以只启用面板更新或只启用内核更新，停止更新使用对应的 `false` 开关。

面板 `0.4.2` 的“保存并重新加载”会应用这四个字段；直接修改 YAML 或只调用保存接口后，仍需完整重载。`GET /configs` 只读返回这四个生效字段；设置页面不另存浏览器更新策略。旧版浏览器里保存的自动更新偏好也不会转换为 YAML。

从内核 `1.0.1` 起，两个更新器分别按下表运行：

| 操作 | 调度行为 |
| --- | --- |
| 启用了对应开关的进程启动 / 重启 | 应用配置和准备网络后，立即异步检查一次，之后按所设间隔检查 |
| 运行中从关闭改为开启并完整重载 | 立即异步检查一次，之后按所设间隔检查 |
| 完整重载相同开关、间隔 | 保留原任务和计时器，不重复立即检查，不推迟下次检查 |
| 保持开启，仅修改间隔并完整重载 | 取消旧自动任务，从该次重载按新间隔计时，不额外立即检查 |
| 关闭并完整重载 | 取消定时器和尚未提交的后台请求，停止后续自动安装 |

启动检查与初始面板下载会在后台等待本次 DNS 连接重置完成，不阻塞配置应用，也不先使用尚未应用完成的网络。策略和取消立即发布，已被关闭或替换策略的旧任务不能因等待结束而恢复执行。构造配置、读取 `GET /configs` 或执行 `mihomo -t` 都不会启动更新任务。

同一类检查与安装共用各自的操作闸门，避免同时改动同一目标。启动 / 启用检查及首次面板安装可取消地等待旧操作释放，避免快速关闭再开启时漏掉检查；等待有上限。周期检查或手动兼容请求遇忙仍直接返回，不积压安装队列。相同面板目录和来源的首次下载会合并，完整重载不会额外创建同一份下载。

调度由内核进程执行，浏览器关闭或面板页面不在前台都不影响检查。网络不可用、下载失败或校验失败时保留现有文件，下一周期继续尝试。下载不阻塞配置重载；最终文件替换与策略变更串行提交，已经过时的任务不能迟到安装。

## 固定面板来源与目录

面板固定从下列仓库静态分支归档获取：

`https://github.com/chummumm/mihomo-optimized/archive/refs/heads/clash-dashboard-dist.zip`

文件安装到 mihomo 配置主目录下的 `ui`，并由控制器 `/ui/` 提供静态服务。使用 `-d /path/to/home` 时目录就是 `/path/to/home/ui`；目录不会由配置文件自身所在的位置或当前工作目录另行推断。旧的路径、URL 和子目录配置只为兼容已有 YAML 而接受，均不影响下载或服务目录，也不再作为可配置入口输出。

如果该目录缺失或为空，内核会在网络就绪后在后台下载初始面板；这属于首次安装，即使周期自动更新关闭也会执行。自动更新开启时，由启动检查承担这次初始安装；关闭时仍安排独立的初始安装。已有文件时不会通过首次安装覆盖，等待操作闸门后以及提交前还会复查目录是否仍为空。初始下载与后续检查共用安装闸门，不会因启动和重载重复安装。

初始下载失败不会填入半成品。自动更新已开启时，下个周期可再次尝试；自动更新关闭时，可修复网络后完整重载或重启，重新触发空目录的初始安装。

### 根据版本号判断面板更新

本地目录和远端归档根目录的 `build-info.json` 中 `version` 字段提供版本。**只有远端版本严格高于本地才允许自动安装。** 相同版本即使文件、摘要或提交号改变，也不会自动覆盖；更低版本不会自动降级。缺失或无法解析版本时不自动安装，且不会改用摘要差异代替版本判断。旧面板的 `name` 和新面板的 `mihomo-optimized` 名称均可读取，不影响版本迁移。

版本按 SemVer 比较，支持可选的 `v` 前缀、预发行标识及构建元数据。例如 `0.4.10 > 0.4.9`，`0.4.0 > 0.4.0-rc.1`；`0.4.0+build1` 与 `0.4.0+build2` 优先级相同。要求完整三段数字。

每次检查读取固定来源归档中的版本信息。使用 5 分钟结果缓存，并在服务器支持时发送 ETag / Last-Modified 条件请求；`304 Not Modified` 可复用已知的远端版本。服务器不提供缓存校验信息时，需要下载归档后才能读取版本。SHA-256 用于验证下载、安装快照和上一代静态资源的完整性，不作为更新条件。

归档最多 64 MiB，展开后最多 256 MiB、10000 个文件及目录节点，单文件最多 32 MiB，路径深度最多 64 层。先下载、安全解包并校验，再原子替换目录；安装前再次检查本地版本和当前策略。失败保留旧面板。只保留上一代有界静态资源，供仍打开的旧页面继续加载；内部暂存、恢复目录和资源记录不由 `/ui/` 提供。

**面板更新不重启内核、不重载配置，也不清理 DNS 缓存或观测。** 已打开页面可在方便时正常刷新获取新文件；更新不会自动刷新并丢弃配置编辑草稿。

以下接口继续兼容已有集成，当前面板只调用后文的统一接口：

| 请求 | 含义 |
| --- | --- |
| `GET /upgrade/ui` | 读取当前版本及已缓存状态，不发起下载 |
| `GET /upgrade/ui?check=true` | 检查固定面板源的归档和版本 |
| `POST /upgrade/ui` | 显式安装固定来源面板，供兼容集成使用 |

状态包含版本、提交、文件摘要、`update_available`、`updating`、只读 `auto_update`、`update_interval` 及可选 `next_check`（RFC3339）。版本不可识别时返回 `reason: version-unavailable` 和 `update_available: false`。接口不提供修改来源或目录的能力。

## 内核自动升级与重启

内核检查固定仓库 [mihomo-optimized 的 Releases](https://github.com/chummumm/mihomo-optimized/releases)。先读取 Latest 的 `version.txt`；确认是可识别且严格高于当前版本的发行版后，后续校验清单和安装包请求都锁定该版本的具体 tag，避免 Latest 在下载途中变化导致混用文件。

新发行版使用 `mihomo-optimized-v<主版本>.<次版本>.<修订版本>`，例如 `mihomo-optimized-v1.0.0`。新命名系列整体高于旧的 `v1.19.x-optimized-N` 系列；新系列内部按三段数字比较。运行中版本不可识别时不自动安装。相同或更低版本也不自动安装，即使强制覆盖的手动兼容接口仍存在。

安装按当前操作系统、CPU 架构及 ABI 选择确切资产名，例如 `mihomo-optimized-v1.0.0-linux-amd64.gz`。先验证发布清单 `SHA256SUMS`，再解包到当前可执行文件旁的临时目录；下载、元信息和解压大小均有上限，取消请求会停止下载和解包。macOS 会对暂存可执行文件执行现有的本地签名步骤。

提交前再次检查更新策略、版本、当前可执行文件身份及 SHA-256。下载期间如有外部程序修改或替换可执行文件，会放弃本次安装，避免覆盖另一次升级。已安装待重启的版本也会记录，防止运行中的旧版本号引起重复安装。旧文件备份到相邻的 `meta-backup` 后才替换。

成功安装会使用内核已有的重启机制，重启时关闭旧 DNS 查询连接和监听器，再启动新版本。内核重启会中断现有代理及控制器连接；启用自动更新表示允许在检查到新版并完成校验后执行这次重启。最终安装和重启与 YAML 重载使用同一个配置事务，关闭或改期的过时任务不会在重载完成后迟到替换或重启。嵌入模式不启用内核自动替换宿主进程。

`.deb`、`.rpm`、`.pkg.tar.zst` 的下载文件名不带发行版本，便于首次部署后由内核自己更新；包内仍有系统包管理器需要的版本元数据。内核自更新只替换可执行文件，**不会修改 dpkg/rpm 等包数据库中记录的安装版本**。实际运行版本以控制器 `/version` 或内核版本报告为准。

旧 `v1.19.32-optimized-13` 内核无法识别新的 tag 格式，需要首次手动迁移到 `mihomo-optimized-v1.0.0` 或更新的新系列内核；迁移完成后才能按上述 YAML 策略继续自动更新。

面板源码及安装说明见 [面板 README](https://github.com/chummumm/mihomo-optimized/blob/clash-dashboard/README.md)。
